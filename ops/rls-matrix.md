## 1. Who the roles are

| Role                    | How the database recognises it                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Owner                   | A `memberships` row with `role = 'owner'`. With `facility_id` null (organization-wide) it gives organization-level rights (`is_org_member`: update the organization, write memberships) and owner rights on every facility of the organization (`is_member`). An owner row with a **non-null** `facility_id` is also accepted by `is_member()` and acts as owner of that facility only (see the open decision D2). |
| Manager                 | A `memberships` row with `role = 'manager'` for one facility, or organization-wide, through `is_member()`.                                                                                                                                                                                                                                                                                                         |
| Guard (membership)      | No policy gives a `role = 'guard'` membership any access to facility data; guards act through their enrolled phone. Like every signed-in user, a guard-member can read their **own** `memberships` row (`memberships_select`, `0010_rls.sql:168-173`). Probed, not tested.                                                                                                                                         |
| Device (enrolled phone) | A Supabase auth user recognised by one of three different rules, listed below.                                                                                                                                                                                                                                                                                                                                     |
| Anonymous (`anon`)      | No privilege on any table or view in `public` (tested, section 6). Function EXECUTE is a separate matter: three helper functions still allow EXECUTE by PUBLIC and therefore by `anon` (section 3, decision D1).                                                                                                                                                                                                   |
| `service_role`          | Server side only (Edge Functions, jobs). Not covered by these policies or column grants.                                                                                                                                                                                                                                                                                                                           |

The schema forbids neither an owner row with a facility nor a guard row: `memberships` has a role check, a foreign key on
`(facility_id, org_id)` and a unique key, and nothing ties `owner` to a null `facility_id` (`0002_staff_devices_memberships.sql`).

| `device_facility()` (every RLS read by a device, the view) | yes                     | yes         | yes                     | yes                     | yes                       | `0010_rls.sql:45-54`               |

(`docs/integrations/ingest-events.md`, "Security model").

## 2. Table matrix

Every public table has RLS enabled (tested). "Owner/manager" means a member of the row's facility (or organization) as in
section 1. A dash means the operation is denied, but **how** it is denied differs:

- Where the table privilege is revoked, the statement fails with `42501`.

## 3. Views and functions

Two things are listed separately because they differ: who may call a function (EXECUTE), and whether it runs with its
owner's rights (SECURITY DEFINER). PostgreSQL grants EXECUTE on a new function to PUBLIC by default; a function is closed to
`anon` only if its migration revokes that. The grants below were read from the SQL and confirmed by a catalog probe. Only `heartbeat`, `ingest_events` and `lock_session` have a committed privilege assertion (in other suites); **no
committed test checks the rest** (section 6).

## 4. Privileges beyond RLS

RLS does not govern `TRUNCATE`, `REFERENCES`, `TRIGGER` or column-level access, so these are set with privileges:

- **No `TRUNCATE`, `REFERENCES` or `TRIGGER`:** `authenticated` holds none on any public table and `anon` holds no table
  privilege at all (tested, `rls_policies.test.sql:343,346`). The catalog assertion covers **table** privileges only, so
  it would catch a future table that keeps the defaults (shown by `zz_future_table`, lines 396-402) but **not** a future
  function that keeps PUBLIC EXECUTE, which is how the three helper functions in section 3 went unnoticed. Function privileges are asserted one function at a time (`heartbeat`, `ingest_events`, `lock_session`); there is no catalog-wide check.
- **PIN material:** `authenticated` and `anon` cannot read or write `staff.pin_hash` or `staff.pin_salt`; `service_role`
  and the table owner are not limited by these grants. Devices get the hashes only through `staff_for_device`. A query that
  **names** a PIN column fails with `42501` instead of leaving it out, **including `select *`** (probed on an organization
  owner; the explicit `select pin_hash` and `select pin_salt` failures for a manager are tested,
  `rls_policies.test.sql:146-147`). A client must list the permitted columns.
- **Device identity:** no application role can write `devices.auth_user_id`; managers can only rename a device or set
  `revoked_at` (tested, `rls_policies.test.sql:137-144,362`).
- **Facility ownership:** no application role can update `facilities.id`, `org_id` or `created_at`, so an owner cannot move a
  facility into another organization (tested, `rls_sync_tables.test.sql:159-180`).
- **Deleting staff and devices:** `events` references `staff` and `devices` with `on delete restrict`
  (`0003_events.sql:47,49`), so a staff or device row that has events cannot be deleted by anyone, owner included. A
  device's `device_heartbeats` row is deleted with it (`on delete cascade`, `0008_device_heartbeats.sql:18`). Probed: an
  owner and a manager could delete a staff row that had no events.
- **Manager visibility of `devices.auth_user_id`:** owners and managers can select every column of `devices`, including
  `auth_user_id` (the Supabase user id of the phone). Read from the column grants and confirmed by a catalog probe.
- **No literal-true policy, and every policy is scoped to `authenticated`** (tested, `rls_policies.test.sql:67,70`).
