## Environment and rotation notes

- Planned environment separation is `dev`, `staging`, and `production`. CLD-01 specifies
  GitHub Actions environments for `staging` and `production`; confirm the development
  secret-storage approach and create projects/environments before entering values.
- Store environment-specific credentials separately. A rotation in one environment
  must not affect another.
- If a key is exposed in chat or logs, rotate it immediately. Remove a departing
  team member's GitHub and Supabase access the same day.
- No routine rotation interval is specified in the project documents. Confirm cadence,
  authorized owners, provider procedures, production reviewers, and the exact secret
  consumers with the team/admin; do not infer them from this inventory.
- Record every completed rotation here by date, variable name, environment, and reason.
  Do not record old or new values.
- CI is configured to scan the checkout with Gitleaks CLI `v8.30.1` in
  `.github/workflows/ci.yml`; the scanner is not considered verified until a CI run
  succeeds. The scan redacts detected values from its output. A GitHub administrator
  must make `secret-scan` a required status check for it to block merges; see
  `docs/development/github-repository-settings.md`.
- `scripts/check-client-bundles.mjs` (T-CLD-01-N1, `pnpm check:bundles`) scans the
  built Console client output (`.next/static` and the prerendered pages) in the
  `check` job, and the gate Android bundle (`apps/gate/dist`) in the `android-bundle`
  job. It fails on the `SUPABASE_SERVICE_ROLE_KEY` name, the text `service_role`, a
  JWT whose role claim is `service_role`, or a `sb_secret_` key, and on the key's
  own value when that variable is set in the environment running the check. CI sets
  no secrets, so CI relies on the pattern rules. Findings name the file, line, and
  rule, never the value. Server output is not scanned because server code may hold
  the key.
